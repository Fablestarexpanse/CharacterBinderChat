# FableChat project rules

## Project shape

Single-user, local-first app. Next.js 16 + React 19 + Tailwind 4 + Zustand, with `better-sqlite3` running synchronously inside the Next server process. `lib/db/store.ts` (`FableStore`) is the only thing that touches SQL.

Two memory layers, both per-character:

- **Drawer 1** — `core_memory` table, one JSON document per character, always injected into the prompt. Served by `app/api/chat/core-memory/route.ts` (GET plus the key-whitelisting PATCH) and `app/api/chat/core-memory/refresh/route.ts` (POST).
- **Drawer 2** — bi-temporal graph (`entities` / `facts` / `relationship_stats` / `commitments`), retrieved into the prompt. Served by everything under `app/api/drawer/`: entities, entities/merge, entities/overview, episode, extract, facts, graph, stats, stats/decay, summary/[entityId] and transfer.

`fable_drawer2/` (sibling directory, tracked in the parent repo) is the Python reference implementation with 77 passing tests. Treat its semantics as the spec when changing bi-temporal behaviour, and keep `lib/db/schema.ts` in step with `schema.py`.

## Conventions that matter here

**Schema changes.** `CREATE_TABLES_SQL` is split on `;` and executed statement by statement. Never put a semicolon inside a SQL comment — it truncates the statement and the table silently fails to create. `_initSchema` only swallows "already exists" errors; everything else throws, deliberately.

**Two migration mechanisms, and which to use.** `CREATE TABLE IF NOT EXISTS` never alters an existing table, so a schema change needs both halves. For a **new column**: add it to `CREATE_TABLES_SQL` (the real shape of a fresh table) *and* add an `addCol` line to `FableStore._ensureColumns`, which ALTERs databases created before it existed. For a **shape change** — a table keyed differently, data that must be rewritten — write a version-detecting step like `migrateToChatScoped` in `lib/db/migrate.ts`, which is what carried v1's character-global memory onto v2's chat scoping.

**Predicates are canonicalized on write.** `normPredicate()` in `lib/db/predicates.ts` snake_cases and maps aliases (`is_located_at` → `located_at`). Both the extract route and the manual facts route must store the canonical form, or fact supersession silently stops working.

**Stat scales differ between drawers.** Drawer 2 stats are **−100..100** (0 = neutral). Core Memory's `relationship_with_user` is **0..100** (50 = neutral). `syncStatsToCore` converts between them. Any new stat bar must know which scale it is on — `((v + 100) / 200) * 100` for Drawer 2, `clamp(v, 0, 100)` for Drawer 1.

**Memory is scoped to a CHAT, not a character.** Every Drawer 1/2 table carries `chat_id`, and every store method takes it as the first parameter. Starting a new chat with the same character is a fresh start; carrying memories forward is an explicit `/api/drawer/transfer`, never implicit. Deleting a chat purges its memory (via `purgeOrphanedChatMemory` on state sync). Schema v1 was character-global; `migrateToChatScoped` in `lib/db/migrate.ts` upgrades old databases, and the store calls it before creating any table.

**Stat deltas are not linear.** `deltaStat` applies headroom scaling toward extremes and ×1.5 loss aversion on negative trust/affection/connection changes, and the Drawer 1 rewrite blends mood with the prior (0.6/0.4) instead of replacing it. These exist because the 200-exchange soak showed linear deltas pin every stat at +100 by exchange ~40, which locks the character's emotional range. Don't "simplify" them back to raw addition.

**Ruptures have inertia.** A bond-stat drop of ≥12 effective points opens a 6-step refractory window (`rupture_recovery` on relationship_stats): positive deltas land at ×0.35 until it drains, and `syncStatsToCore` sets `relationship_note` so the prompt carries the wound. Don't bypass `deltaStat` with `setStat` for story events — it skips all of this.

**Embeddings are optional infrastructure.** `lib/llm/embeddings.ts` uses local Ollama (`nomic-embed-text`) with a 60s unavailability cache; every caller must handle `null` and fall back to lexical ranking. Vectors are L2-normalised at creation so `cosine()` is a plain dot product. Never make retrieval *require* embeddings — local-first means Ollama may not be running.

**Eval harnesses spawn Next directly** (`process.execPath` + `node_modules/next/dist/bin/next`), never via `npx` with `shell:true` — the shell wrapper orphaned real servers three separate times, and Next 16 refuses to start while an orphan owns `.next`.

**Stat direction is `character -> player`.** `relationship_stats` rows are directed: observer is the character, target is `player`. That matches what `relationship_with_user` means and what the prompt injects. Querying `player -> character` reads an empty set — that bug shipped once already.

**Entity ids from the model are untrusted.** Extraction will mint `ronan` next to an existing `char-ronan` however the prompt is worded. `EntityResolver` in the extract route folds incoming ids onto existing entities by normalized name before anything is written; never bypass it when adding a new write path. The response's `remapped` field shows what got folded — a growing list means prompt anchoring is losing.

**`lib/server/` is server-only.** Modules there touch SQLite through `FableStore` and must never be imported from a component — the path is the statement, replacing a header comment nothing enforced. `lib/chat/` is client-safe and runs in the browser.

**Client-side generation.** Providers are called from the browser, not from route handlers. `lib/chat/generation.ts` owns the whole turn (prompt build → token budget → stream → extraction). `isGenerating` lives in the Zustand store so every component sees it; the `AbortController` is module-local because it isn't serialisable.

**Persistence is two-layer.** `localStorage` (zustand persist) is a same-browser cache; SQLite is the durable copy. `StateSync` hydrates from `/api/state` on load, then mirrors changes back with a debounce. `PUT /api/state` is a full replace, guarded against wiping existing data with an empty payload.

**Hydration.** Everything is `"use client"`, but Next still server-renders the first pass. Never render a value derived from the current clock (`formatRelative`, `Date.now()`) without gating it behind `useHydrated()`. Placeholder data uses fixed `seedTime()` offsets rather than `Date.now()` for the same reason.

**UI primitives are hand-rolled.** `components/ui/` wraps native elements with Tailwind classes; Radix is pulled in only where focus trapping and portalling have to be correct, which today is `dialog.tsx` alone. `"use client"` marks the primitives that genuinely need it (state, or a client-only portal) rather than every file in the directory.

**Effects must not call setState synchronously.** React Compiler lint rules are on and `react-hooks/set-state-in-effect` is an error. The pattern used throughout the inspector: hold one result object keyed by what was fetched, derive `loading` from `result.key !== fetchKey`, and only setState inside async continuations behind a `cancelled` guard.

**One success envelope per route kind.** Reads return the bare payload (`{ facts }`, `{ entities }`); mutations return `{ ok: true, ... }`; every non-2xx body is `{ ok: false, error }`, which `routeError` in `lib/api/server.ts` guarantees for the 500 path. Clients branch on `res.ok` for reads and on `body.ok` for mutations — three different success checks across the inspector was the bug this replaced.

**LLM output is untrusted.** `parseLLMJson` returns a fallback on unparseable input, so callers must distinguish "parse failed" from "nothing found" and report it rather than returning `ok: true` with empty arrays. Route bodies are validated explicitly; `PATCH /api/chat/core-memory` whitelists keys because the patch is spread into the stored document.

**Access control is `proxy.ts` + `lib/security/access.ts`.** The npm scripts bind `127.0.0.1`; the proxy refuses any non-localhost `Host` unless `FABLE_PASSWORD` is set (then HTTP Basic auth covers everything), and refuses cross-origin writes, because routes parse JSON whatever the Content-Type. A new route needs nothing — it is covered — but never read `req.json()` from a path that skips the proxy matcher. Limit: `Host` is client-supplied, so the loopback bind is the real protection when no password is set.

**API keys are encrypted at rest.** `lib/server/secrets.ts` (AES-256-GCM, key in `data/.fable-secret` or `FABLE_SECRET_KEY`); `/api/secrets` whitelists names; `SecretsSync` keeps the OpenRouter key out of localStorage once the server has confirmed it holds it. Never add a secret to `app_kv` outside that whitelist, and never to the state export.

**Branching is point-in-time.** `lib/db/branch.ts` filters timestamped memory by a cutoff and reopens facts whose superseder had not happened yet. Stats and core memory are current-state only, so they come from `memory_snapshots` (saved when a message's extraction finishes); without one the branch is flagged `approximate` — never silently exact. The branch route writes the chat row and the memory in one request because `purgeOrphanedChatMemory` deletes memory for chats not in `app_chats`.

**Facts can be pinned and locked.** Pin: always injected ahead of ranking, capped at half the window. Lock: `assertFact` returns `duplicate: true, blockedByLock: true` for a conflicting extracted value, and `supersedeFact` skips locked rows unless forced. Hand-entered facts pass `respectLocks: false`. New write paths that supersede must go through `supersedeFact`.

**State sync is incremental.** `StateSync` PATCHes a diff (`lib/sync/stateDiff.ts`) by object identity; PUT is first-run seeding only. A new synced collection needs a row in `APP_COLLECTIONS`, the client's `SYNCED_COLLECTIONS`, and the diff's `SyncedName`.

**Messages have a channel and attachments** (`lib/types.ts`; helpers in `lib/chat/channel.ts`). `channel` is omitted for in-person lines and `"text"` for phone texts; a reply takes the channel of the last user message (`replyChannel`). A line you write that says you text someone in the chat (`I text Ronan "…"`, `*I text him* "…"`, `text Ronan: …`) is sent as that text, the quoted words only, and the box switches to texts (`parseTextIntent`); a line with more story after the closing quote is left as written. The model reads messages through `historyContent` (texts prefixed `(by text)`, ready attachments as `[sent a photo: …]`); never claim a pending or failed attachment. The text instruction is the editable `chat.text-message` prompt, read in the browser through `clientPromptTemplate` (cached 10 s). Attachments are assets with the prompt and settings that made them; the older `imageJobId` image cards are kept as they are. Photo messages are `lib/chat/photos.ts`: a `[photo: …]` line is acted on only when `mayOfferPhotos` (the server-held **Contact & media** switch, `/api/contact-settings`, off by default, AND the character's `contact.photos`); otherwise it is left as text and the offer prompt is never sent. `startPhoto` creates the attachment (awaiting review when `reviewMedia`), `makePhoto` draws it through `settingsForPerson`, stores it with `storePicture` and records a `sent_photo` fact. New media kinds should follow the same switch → attachment → review → asset → fact path. Characters reaching out is `lib/outreach/`: `rules.ts` decides (pure, unit-tested; hard limits first: master switch, pause, Do not disturb, the character's `contact.canContact`, quiet hours, daily limits, silence and follow-up backoff), `runner.ts` reads the chat and core memory and, only when the rules say so, calls `generateAssistantReply` with an `OutreachRequest` (the editable `chat.outreach` prompt becomes the last turn; the reply is a text carrying `outreach.reason`). It runs in the open tab via `OutreachRunner`; in development `window.fableOutreachTick()` runs one check. A model is never asked whether to reach out.

**Memory and image prompts run on the background model, not the chat model** (`lib/server/backgroundModel.ts`, `/api/background`, Settings → Memory). The chat's model may be a paid cloud one, and these jobs run after every reply. The memory routes (extract, core-memory/refresh, episode) take `background: { ollamaBaseUrl, utilityModel }` and swap their backend through `withBackground`; the scene director calls `backgroundModel` itself. Order: Ollama on this computer (FableChat starts `ollama serve` if it is installed but not running) with the memory model (`MEMORY_MODEL`, `qwen3:4b-instruct-2507-q4_K_M`, downloaded into Ollama from the Settings card), else the chosen utility model; the request's own provider only when `fallbackToChat` is on (off by default, so nothing is spent without the user choosing it); otherwise a 502 saying what to do. A new background job must go through the same function. Model output is untrusted: read text fields through `text()` in the extractor, never `.trim()` on a raw field. `callOpenAICompat` always sends `max_tokens` (`DEFAULT_MAX_TOKENS`): without it OpenRouter reserves credit for the whole output window and answers 402.

**Pictures only use workflows ComfyUI can run.** `lib/chat/workflowNodes.ts` asks ComfyUI (through the `/api/comfyui` proxy, one request per node type, cached) whether a workflow's `classTypes` exist; the likeness workflow is chosen only when they do, so a missing custom node (IPAdapter for the bundled face-ID workflow) means a normal picture rather than a rejected job. A LoRA pipeline with no LoRA to apply is queued as its plain workflow (`plainWhenNoLora`, `PLAIN_FOR_LORA_PIPELINE`, applied in `queueImage`).

**Prompt assembly is `assemblePrompt`.** Peek Prompt previews through the same function generation uses; keep it free of side effects (the context meter is set by the caller).

**A character's (or persona's) image look is `image`** (`lib/media/imageLook.ts`: tags, avoid, lora, seed). It is for image models only, never the chat prompt. On cards it lives under `extensions.fablechat.image` (`withImageLook`/`splitImageLook` in `tavern.ts`; lifted out of `cardExtensions` on import so it is not stored twice). Anything from outside (cards, agents) goes through `cleanImageLook`. Every path that makes a picture of a character must pass the settings through `applyImageLook`: today `/image` (`generateSceneImage`) and the Images tab (**Draw as**). Do not merge two people's looks into one prompt. Reference pictures are `referenceImages` on the row (asset URLs, primary first; not a card field, so not exported): `referencesFor` picks them (the portrait when there are none), `withReferences` puts them in the settings, and `ComfyUIProvider.prepareWorkflow` uploads them into the workflow's `referenceImageNodes` via `injectReferences`. With `image.likeness` on ("Make pictures look like them"), `settingsForPerson` also switches to a likeness workflow (`likenessWorkflow`: the user's photo/portrait workflow with an image input, else the bundled `sdxl-faceid-likeness`); new picture paths should call `settingsForPerson` rather than the pieces.

**ComfyUI workflows are read, not hand-mapped.** `lib/media/workflowDetect.ts` walks an API-format graph from the sampler back to the text, seed and size inputs (following pass-through and primitive nodes, and the *side* a two-sided node like `WanImageToVideo` was reached from) and writes the result to `_meta.fablechat`, which `applySettingsToWorkflow` already reads. Bundled templates in `workflows/` are read-only; imported ones live in `app_kv` (`workflow:<slug>`, index `workflows:imported`) through `lib/server/workflows.ts`, and `/api/workflows/<slug>` serves either. The detector must keep reproducing the bundled templates' hand-written mappings (`tests/unit/workflowDetect.test.mjs`). The window-wide card importer (`DropImport`) steps aside on the Workflows screen.

**Media services are server-side connections** (`lib/media/connections.ts` for the shape and catalogue, `lib/server/mediaConnections.ts` for storage and calls, `/api/media/connections` and `/api/media/test`). Unlike the chat providers, media requests are made by the server, so a media key is stored as `secret:media:<id>` (encrypted, stripped from backups) and is never returned to the browser, only `hasKey`. Defaults are per purpose (`portrait`, `photo`, `scene`, `video`, `voice`, `stt`); resolve one with `connectionFor`. Defaults are saved as a patch, never a replacement, so two quick changes cannot overwrite each other. A new service needs a `MEDIA_PROVIDERS` entry, a case in `testConnection`, and a stand-in in `tests/unit/mediaConnections.test.mjs`.

**Prompts the app sends behind the scenes are templates** in `lib/prompts/defaults.ts` (ids, text, `{{variables}}` with descriptions), rendered by `lib/prompts/render.ts`. Builders take the template as a parameter and stay pure; server callers pass `promptTemplate(id)` from `lib/server/prompts.ts`, which returns the user's override (`prompt:<id>` in `app_kv`, so it is in backups) or the default, and falls back to the default if an override stops passing `checkTemplate`. A new prompt needs a registry entry, its builder taking the template, and the caller using `promptTemplate` (in the browser, `clientPromptTemplate`); the prompts test checks every registry entry declares exactly the variables it uses. The fixtures in `tests/unit/fixtures/` pin what the builders produced *before* prompts became templates, so only those builders have one; a new prompt needs no fixture. Changing a default's text means regenerating `prompt-defaults.json` on purpose, and running `npm run eval:gate` for the memory prompts.

**The extraction gate is deliberately dumb.** See `docs/extraction-gate.md` before changing it: content-based skipping was measured and rejected. Run `npm run eval:gate` after touching it.

**Cards are `lib/cards/`.** `png.ts` is the only PNG codec (read and write); `tavern.ts` owns Character ↔ Tavern V2 and `expandMacros`. Import (`lib/import/cardFile.ts`) and export (`lib/cards/export.ts`) both go through it, so a field is added in one place and round-trips. A new `Character` field needs: the type, `characterToCard`, `cardToCharacterDraft`, the editor form, and a line in `tests/unit/cardsTavern.test.mjs`. Anything the editor does not show but the card carries (`cardExtensions`, `characterVersion`) must be passed through on save — `CharacterEditorDialog` builds the character from the form, so a field missing from `handleSave` is silently dropped. A new `LoreEntry` field needs the type, `entryTriggered` if it changes matching, `convertLoreEntry` (import), `loreToCharacterBook` and `lorebookToCard` (export), and `tests/unit/lorebookCards.test.mjs`. `textParser.ts`, `platforms.ts`, `convert.ts` and `validate.ts` are ported from CharacterBinder and carry its tests via `tests/unit/_vitest.mjs`; change their behaviour only with the tests. A new platform needs a registry entry (including its field-support table) AND a converter, or the "writes every field it claims to keep" test fails. Archive import (`lib/import/archive.ts`, `lib/cards/zip.ts`) reads untrusted files: keep the entry-count and inflated-size caps, count what was produced rather than what a header declares, and keep imports idempotent (duplicates skipped). The migration plan is `docs/merge-characterbinder.md`.

**Card text has placeholders.** `{{char}}` / `{{user}}` are expanded once, over the whole assembled system prompt (`buildSystemPrompt`) and in opening messages (`fillGreeting`). Never send card-sourced text to a model another way.

**The server is authoritative; the tab is a cache that syncs.** Every write to app state bumps a revision (`bumpRev` in `lib/db/appState.ts`) and stamps its rows; deletions leave tombstones. Never write `app_*` tables except through `patchAppState` / `replaceAppState`, or the revision, tombstones and every open tab's view go stale. `SERVER_WINS` collections (characters, lorebooks, personas, scenarios, presets) keep the server's copy when a stale write arrives; **chats are browser-wins** — do not make chats server-wins, a streaming reply dirties its row on every token. The tab's merge policy is `lib/sync/remote.ts`; change it only with its tests. `StateSync` must pull before it saves and must re-baseline rows it took from the server, or the next diff sends them straight back.

**Outside writers go through `lib/server/cards.ts`**, never straight to SQLite: it validates, converts card formats, keeps the previous version (`app_history`) and records an event (`app_events`) in the same transaction as the write, so the change is atomic, attributable and undoable. A new card field must be added to `CHARACTER_FIELDS` there as well as to the editor, or `update_card` will refuse it. `mcp/tools.mjs` holds no card logic on purpose; keep it that way.

**Images are assets, never inline.** `lib/db/assets.ts`: content-addressed rows in `app_assets` (the SHA-256 of the bytes), type sniffed from the bytes (images PNG/JPEG/GIF/WebP, never SVG; with `?kind=video` MP4/WebM, with `?kind=audio` WAV/MP3/OGG/FLAC; served with Range support), referenced from rows as `/api/assets/<hash>`. In the database rather than on disk so backup and restore stay one file. Display goes through `Avatar`, which asks for `?w=` (resized by `sharp` when present — it is an optional dependency, so the original is served without it). Upload with `imageToAvatar` (`lib/chat/assets.ts`), which keeps the original for export. On open, `getStore()` moves any inline `data:` avatars into assets (through `patchAppState`) and `gcAssets` sweeps unreferenced ones older than a day — it counts references in rows **and** `app_history`, so an undo can still bring an old picture back. A new place that stores an image must store a reference, or history, sync and localStorage bloat again.

**The Library is the one card screen.** `components/sections/LibraryView.tsx` lists characters, personas, lorebooks and scenarios; lorebooks and scenarios are edited in their own sections, reached by setting `focusCardId` (ui store) so the section opens and scrolls to that card. Starting a chat goes through `useStartChat` (`components/characters/StartChat.tsx`), which offers the memory chooser; do not call `createChat` from a button directly. Archive export is `exportArchive` in `lib/cards/export.ts` → `buildArchive` (`lib/cards/archive.ts`, CharacterBinder's layout) → `writeZip`; it must stay readable by `lib/import/archive.ts`, which `tests/unit/archiveExport.test.mjs` checks. An embedded lorebook that matches one already in the store (name and entries) is linked, not copied (`linkOrImportBook`).

**A new install opens on the demo story** (`lib/demo.ts`: Port Ellery: June and Elias, the Nora and Theo personas, each with a demo voice, the Port Ellery lorebook, a scenario and a chat with June a few lines in, all with `demo-` ids; no portraits, since the app ships no images). The sync engine adds it in its first-run branch only when the server's `rev` is 0 **and** the tab holds nothing, so deleting it is permanent (an emptied library has rev > 0) and a tab with its own cache never gets it. `addDemoStory` skips ids already present and keeps an existing active persona. It matches the README screenshots; change both together.

**Renders are kept by copy, and deleting one says who kept it** (`lib/media/renders.ts`, `components/image/UseRenderDialog.tsx`). A render's `outputUrls` are ComfyUI URLs; anything that keeps one (Image Studio's **Use for a character**, an image card's Keep as reference) stores it with `storePicture` first and records the asset URL on the job as `keptAs[outputIndex]`, so `renderUsage` can answer "what uses this?" by URL. Deleting goes through `deleteRenders`, which removes the job and its chat image cards together and returns what it took for `restoreRenders` (Image Studio's Undo bar); a kept portrait or reference is its own asset reference and stays. A new place that keeps a render must record `keptAs` too.

**Pictures you send are read once, then told** (`lib/chat/userPictures.ts`, `/api/vision/describe`, `lib/server/vision.ts`). An attachment with `fromUser: true` is described by the picture reader (`providerSettings.vision`: a model that can see images, via Ollama `images` or an OpenAI-style `image_url` part; OpenRouter uses the server-held key) with the editable `image.describe` prompt, and the description is its `prompt`, so the chat model reads `[sent a photo: …]` like any attachment and needs no vision itself. The reply waits for the reading; a failed or missing reader still sends the picture and you can describe it on the message. The image itself is never put in the chat prompt.

**Phone calls are a channel, not a mode** (`lib/chat/calls.ts`, `components/phone/`). Lines said on a call are messages with `channel: "call"` (the model reads `(on the phone) …` and the editable `chat.phone-call` prompt); a call starting, ending, being missed or declined is a message with a `callEvent` and empty content, which `historyContent` turns into `[phone call starts]` etc. Call state lives in the ui store (`call`). Nothing pops up over the screen when something arrives: a ringing call shows on its chat row in Recent Chats (Answer / Decline there), texts and missed calls as a red count on the row's portrait plus a small type badge, and the phone menu button carries the total. `CallScreen` takes over only once you are calling or connected. Characters ring only through the outreach rules: `reachOutBy` (pure, tested) picks a call for repair/absence when the character's `contact.calls` is on, and `decideRandomCall` adds calls now and then at the pace in `contact.randomCalls` (up to `perDay`, at least `gapHours` apart, never within 15 minutes of your last line; the per-minute chance is `perDay` over the waking minutes, and `rand` is passed in so it stays pure); a missed or declined call carries `outreach` so it counts toward limits and backoff. Their lines are captions until a voice connection exists. Sounds are `lib/chat/sounds.ts` (Web Audio, no files), behind the Contact & media `sounds` switch. Development-only console hooks: `fableRingIn()`, `fableTextIn(chatId)`.

**Voice is VibeVoice, run by FableChat** (`voice/fable_voice/`, a small Python server; `lib/server/voiceRuntime.ts` installs and runs it, `lib/server/voiceSpeak.ts` speaks). Nothing is downloaded until you press Set up in Settings → Media → Voice: uv, a Python 3.11 venv, PyTorch, the engine (SanDiegoDude's fork, pinned to a commit, installed `--no-deps` because `aiortc` will not build on Windows), the model, its Qwen2.5 tokenizer and the vocal-isolation model, all into the folder you chose; `voice:runtime` in `app_kv` records it. The server runs offline (`HF_HUB_OFFLINE`), binds 127.0.0.1, refuses any other `Host`, and answers only requests carrying `X-Fable-Voice-Token` (a fresh token per start, in the child's environment and `<folder>/.server-token`; send it with `voiceHeaders()`); a 403 is reported as "something else is on the port", never retried around. The model lives in a worker process that exits when idle (the GPU memory goes back) and when its parent dies; jobs are acknowledged (`taken`) so one lost to an idle exit is resent once. A character's or persona's voice is `voice` (`lib/media/voice.ts`: an uploaded sample as an audio asset URL with a `consent` tick, or a demo voice); `cleanVoice` drops a sample without consent. It is a row field, not a card field, so it is not exported; so are lorebook and scenario `banner`s (770 × 110 asset URLs, shown in their sections and the Library). The voice server keeps its own copy of each sample, named after the asset hash and cleaned once by vocal isolation (trimmed to 60 s first, run in its own short-lived process). `voice:runtime` and `media:saveFolder` are `MACHINE_KEYS` in `lib/db/backup.ts`: left out of backups and kept from the live database on restore, because a restored folder path is a path FableChat would run `python.exe` from. Replies are spoken by `lib/chat/speech.ts`: `spokenText` picks what is said (a text or call line whole; a story reply its quoted words, else its narration without *actions*), the audio is made through `/api/voice/speak?store=1` in the writer's voice and kept on the message as `speech: { url, key }`, where `key` is the voice plus a hash of the words, so a replay costs nothing and an edited reply or a changed voice is spoken afresh. `chat.readAloud` speaks each new reply once as it finishes (`readAloudIfOn`, called from generation); one thing plays at a time (`speaking` in the ui store). With a narrator (`voice:narrator` in app_kv, `/api/voice/narrator`, Settings → Media → Narrator) `speechParts` splits a story reply into narration and quoted speech and the two voices are sent as one `/v1/dialogue` clip; narration goes out as plain text because the voice server's `clean_line` would drop an *action* as a stage direction. `partsKey` keeps a reply that is all speech under its old `speechKey`, so audio made before the narrator still plays. The asset sweep counts `app_kv` (never `secret:*`), so a sample referenced from a setting is kept. Plan and status: `docs/plan-voice.md`.

**Chat media can also be copied to a folder** (Settings → Media, `lib/server/mediaFolder.ts`, `/api/media/save-folder`). The asset in the database stays the real copy; `POST /api/assets?copy=1&who=<name>` additionally writes `<folder>[/<who>]/<date>_<who>_<photo|clip>_<hash8>.<ext>`. The folder is checked (absolute, created, writable) before it is kept, names go through `safeSegment`, and a failed copy is returned as `saveError`, never a failed upload. Only photos and clips made in chats ask for a copy; avatars and reference uploads do not.

**Settings is tabbed.** `SETTINGS_TABS` in `lib/store/ui.ts` lists the tabs; `SettingsView` puts each card in a `Panel`, and every panel stays mounted (only hidden) so a half-filled form survives a tab switch. A new card goes into a tab, not below the list. To send someone to a card, `setSettingsTab(id)` before `setActiveSection("settings")`.

**Dialog editors guard unsaved changes** with `useDiscardGuard(dirty, close, closeRef)` and `DiscardBar` (`components/ui/discardGuard.tsx`). The dialog's `onOpenChange` must call `closeRef.current`, not the close function, or Escape and the × skip the question. A new modal editor needs the same wiring; inline editors that save as you type do not.

**Narrow screens (< 768 px) swap two pieces, not the whole layout.** `useNarrow()` (`lib/hooks/useNarrow.ts`, `useSyncExternalStore` over `matchMedia`) decides; `app/page.tsx` renders `NavDrawer` + `MobileBar` instead of the in-flow `Sidebar`, and `InspectorPanel` becomes a sheet driven by `inspectorSheetOpen` (separate from the desktop `inspectorOpen`, so a phone never opens with the chat covered). The drawer is open *at* a place (`navOpenAt` = `section|chatId`), so navigation closes it without an effect. Buttons never wrap (`whitespace-nowrap` in `Button`); rows that would crush a name hide secondary badges below `sm`. A new header or toolbar must fit 390 px: check with a script that looks for elements past the viewport, since `overflow-hidden` ancestors hide the problem from the eye.

**Deleting must not leave dangling references.** `lib/chat/references.ts` answers "what uses this?"; the delete UIs say it, `deleteLorebook` clears `lorebookId` on characters and removes the id from chats' `lorebookIds`, and the agent path (`deleteCard`) does the character half in the same commit so one undo restores both and returns `usedBy`/`warning`. A chat whose character no longer exists refuses to generate (`speakerIsMissing`) instead of quietly answering as a generic assistant; a deleted group member is not eligible to speak (`presentMemberIds(chat, characters)`). A new reference between rows needs the same three things: a usage question, cleanup on delete, and a test.

**Backup is a database snapshot, and restore swaps the file.** `lib/db/backup.ts`: `writeBackup` uses SQLite's online backup, stamps it, strips `secret:*` keys and vacuums; `swapInDatabase` validates first (magic bytes, `integrity_check`, required tables), renames the old database (never deletes it; the newest three are kept), restores the live API keys into the new file, and mints a new **epoch**. Tabs compare epochs on every poll and reload when it changes: revision numbers mean nothing across databases. Add a table the app needs to `REQUIRED_TABLES` only if an older backup would be unusable without it, or old backups become unrestorable. The JSON export (`/api/state?download=1`) deliberately omits memory; do not describe it as a backup.

**The sync loop lives in `lib/sync/engine.ts`, not in a component.** `StateSync` only mounts it through `createLifecycle`, because React's development double-invoke runs an effect's cleanup right after its first run; a loop whose cleanup disposes it then silently never starts (no polling, no saving, in development only). Unit tests cannot see that class of bug: after any change to sync, run it in a browser and confirm `/api/state/changes` is being requested.

## Before you finish

`npm run lint` and `npx tsc --noEmit` are both expected to be clean. Verify UI changes in the running app rather than assuming.
