# Audit: FableChat after merging CharacterBinder

**Date:** 2026-11-04 · **Branch:** `claude/cool-fermat-e5ednj` · **Scope:** the whole program as it stands, with
emphasis on what the merge left missing, left broken, or left unintegrated.

**Method.** Everything below was run or read, not assumed. Production build; `npm audit`; the unit, API and MCP
suites; the access guard against a *production* server; live browser runs at phone, tablet and desktop widths and in
dark mode; measurements where a claim could be measured. Each finding says whether it was **verified** (run it,
saw it) or **read** (from the code, not exercised). Effort is S (under a day), M (days), L (a week or more).

---

## Verdict

The merge works: a card made anywhere can be imported, edited, exported, round-tripped, migrated from a
CharacterBinder archive, and driven by an agent, and the memory/sync layers underneath are in good shape. What it is
**not yet** is something you can hand to another person as "the one thing to launch". Five gaps stand between here
and that, and four of them are things the old tool did that this one doesn't do yet: a launcher, a real backup, a
usable library, and narrow-screen layout. The fifth is security hygiene that should be fixed before anyone else runs it.

---

## What is solid (verified)

- **Build, types, lint** clean; `next build` succeeds. 389 unit tests, 22 API/MCP tests pass. (The single failing
  unit test needs the sibling `fable_drawer2/` directory and has failed in this container since before the merge.)
- **Access guard holds on a production server**, not only in dev: wrong `Host` → 403, cross-origin write → 403, page
  with a wrong `Host` → 403, percent-encoded path trick → 403.
- **Sync**: an agent's create/edit reached an open tab in ≤3 s with an Undo; an idle tab wrote nothing (revision
  stable); a true same-field conflict resolved to the server's copy with a warning; a streaming chat is protected.
- **Round trips**: character → PNG/JSON → import preserves every card field and the art; archive import is idempotent
  and survives hostile zips.
- **Theme**: dark mode and a custom accent render correctly across the new UI.
- **The agent path is safe to leave on**: every change is reversible and attributed.

## Tier 0 — fix before retiring CharacterBinder or letting anyone else run it

### 1. The installed Next.js has critical advisories — **verified**, S
`next@16.2.6` is in range for 20 advisories, **five of them critical remote-code-execution**. Four of those concern
features this app does not use (image optimization, `next/og`, `use cache` — searched, none present), so the real
exposure is narrower than the headline. The two that do not depend on features are the **unauthenticated RCE on
Windows-hosted servers** (relevant if your users are on Windows, which a double-click launcher suggests) and a
**Middleware/Proxy bypass under Turbopack**, the mechanism the access guard (`proxy.ts`) relies on. Several
Server-Actions DoS/SSRF advisories also apply in principle; the app uses no Server Actions. I tested the fix in a throwaway upgrade and reverted it: **`next@16.4.5` is a semver-minor
bump; `tsc`, lint, production build, 389 unit tests and all 22 API/MCP tests pass, and the audit drops from 19
vulnerabilities to 15 with no criticals left.** Do this first.
- It also silently rewrites the Next block at the top of `AGENTS.md` the first time `next dev` runs (observed);
  commit that change with the upgrade.
- *Defense in depth:* the guard lives only in `proxy.ts`. If a future Next bug skips the proxy, every route is open.
  Cheap insurance is a one-line `assertLocalAccess(req)` in the few routes that matter (`/api/state`, `/api/cards`,
  `/api/secrets`), reusing `lib/security/access.ts`.
- Separately, `zod@3` (added for the MCP server) carries a high advisory with a major-version fix. Real exposure is
  small (inputs come from your own agent), but track the SDK's zod 4 support.

### 2. There is no LICENSE, and the repo now contains MIT-licensed code — **verified**, S
The text parser, platform registry, converters, validator, PNG codec and their tests were ported from CharacterBinder
(MIT, © PromptWaffle). MIT requires the copyright and permission notice to travel with the code. Add a `LICENSE` for
FableChat (your choice) and a `THIRD_PARTY_NOTICES.md` carrying CharacterBinder's MIT text. (Marinara Engine is AGPLv3;
nothing was copied from it, only ideas.)

### 3. The backup leaves out the memory, and there is no restore — **verified**, M
Settings → "Export chats & characters (JSON)" calls `getAppState()`, which reads only the `app_*` tables. It contains
**no facts, core memory, relationship stats, scene cards, commitments or branch snapshots**, which is the part of the
product that is hard to recreate. And there is no import/restore of that file at all. Someone who relies on the
export loses their characters' memories on a disk failure.
- **Fix:** a full backup using SQLite's online backup API (`better-sqlite3` `.backup()`), downloaded as one file, plus
  a restore path with a schema-version check and a "this replaces everything" confirmation. Keep the JSON export
  as the portable, human-readable option and say what it omits.

### 4. "Launch one thing" isn't true yet — **verified**, S–M
CharacterBinder shipped `start.bat`/`start.sh`: check Node, install on first run, start, open the browser, and just
open a tab if it was already running. FableChat has none. The README says `npm install && npm run dev`, which runs the
**development** server (slow start, file watching, a dev overlay on screen), and nothing checks the environment.
- Add `start.sh` / `start.bat`: Node version check, `npm ci` on first run, `next build` once (rebuild when the
  version changes), `next start`, port-in-use handling, open the browser.
- Declare `engines`: the unit tests rely on Node's built-in type stripping (22.18+/24), the README says "Node 20.9+",
  and `package.json` has no `engines` field — verified. Pick one truth.
- Windows users are the likely audience for a double-click launcher; `better-sqlite3` can need a prebuilt binary or a
  compiler there, which the launcher should detect and explain rather than fail with a stack trace.

### 5. Deleting things silently degrades other things — **verified/read**, S–M
- Delete a **character** and its chats keep a dangling `characterId`. **Read:** generation does
  `character ? fetchCoreMemory(...) : NO_MEMORY`, so the chat keeps working but as "You are a helpful assistant" with
  no memory, and nothing says so. An agent can now do this through `delete_card` (reversible only while its history
  lasts).
- Delete a **lorebook** and a character's `lorebookId` still points at it (the editor's dropdown then shows blank).
- **Fix:** referential checks. The delete response (UI and API) should say what depends on it ("3 chats use Ash"),
  the UI should ask, and dangling links should be cleared. `delete_card` should return `usedBy` so an agent can
  mention it.

### 6. Images live inside JSON, and it already costs — **verified**, L (highest-leverage change)
Avatars are base64 strings inside the character row. **Measured:** 40 agent edits of one character with a typical
45 KB avatar grew the database by **6.5 MB** (including its write-ahead log), because the undo history stores the whole prior row
each time. At the 500-row cap that is on the order of 30 MB for one heavily edited character. The same blob is also in
`localStorage` (the persisted store includes characters; browsers commonly allow about 5 MB per origin), in every `PATCH`, and in every changes-poll response. It also fixes nothing about export quality:
avatars are stored as 512 px JPEGs, so every exported PNG card has degraded art and the original is gone.
- **Fix:** a small **asset store**: files on disk under `data/assets/<sha256>`, served from `/api/assets/<hash>`, rows
  hold only the hash. That one change shrinks history, sync payloads and localStorage; keeps the original art for
  full-resolution export; deduplicates; and lets agents set avatars (the MCP server currently cannot).
- Until then: stop storing avatars in history rows (store the hash/size, or skip binary fields), and cap history by
  bytes, not rows.

## Integration across the program

1. **The inspector hides most of the card.** The Character tab shows tags, description and personality (verified by
   search). Scenario, first message, example dialogue, system prompt, post-history, alternate greetings, creator notes
   and the linked lorebook are not shown anywhere outside the editor dialog.
2. **Alternate greetings exist only in the new-chat dialog.** The quick "Chat" button, group chats and "clear chat" all
   use the main greeting (verified by search). There are no swipes through alternates.
3. **Lore and memory don't know about each other.** The extractor can re-learn as a fact what a lorebook entry already
   says, so the same thing is spent twice in the prompt ("Known Facts" and "World Lore"). Retrieval could suppress
   facts that overlap an injected lore entry, and the Facts view could offer "promote to lore". Lorebooks show no
   "used by" indicator, and the Lore tab doesn't say which book belongs to which character.
4. **The agent surface stops at cards.** MCP exposes 11 tools, all about cards, and none for the app's differentiator, memory: no
   list/add/edit/pin/lock facts, no reading a chat or core memory, no starting a chat, no presets, no avatars. The
   revision and event machinery makes these cheap to add.
5. **Agent activity is a transient banner.** Events are persisted server-side, but the UI shows only a capped, in-session
   toast stack with Undo; reload the tab and the Undo is gone. A Settings → **Activity** list (recent outside changes,
   who, when, Undo) would use data that already exists.
6. **Settings is provider-centric.** Missing: Backup/Restore, **Agent access** (how to connect, status, the command to copy,
   whether a password is set), **Security status** (bound to localhost? password? key file location?), data location,
   version/update info. The "Export cards for" platform choice resets on reload.
7. **Three notification systems** (red sync banner at the top, an amber inline export notice, bottom-right remote
   notices) behave differently and none persists. There is no at-a-glance sync state (synced / saving / offline /
   conflict) anywhere.
8. **Navigation has grown to ten sidebar items** (Characters, Chats, Groups, Lorebooks, Scenarios, Presets, Image Studio,
   Gallery, Workflows, Settings). Characters, Lorebooks and Scenarios (and Personas, which live inside the Characters page) are one mental model,
   "my cards"; a single **Library** with tabs, search and tags would match how CharacterBinder organised it and replace
   three sidebar entries. There is no cross-entity search.
9. **Narrow screens are broken** — **verified** at 390 px: the fixed 220 px sidebar leaves the chat 170 px wide with
   text wrapping one word per line, and the inspector overlays it. The README's own roadmap still lists "Mobile
   layout" as undone. Now that LAN/phone access is a documented feature, this matters: sidebar as a drawer, inspector
   as a bottom sheet below ~768 px. (820 px tablet is usable.)
10. **No first-run path.** An empty install shows empty lists. The shortest route to a working chat (connect a provider →
    import or create a character → start) is not guided.
11. **The eval harness is out of date.** `tests/memory-eval/long-chat.mjs` mirrors the prompt builder by hand and does
    not know the card sections or macro expansion, so the soak results describe a prompt the app no longer sends for
    characters that use them. Add a scenario built from a complex imported card.

## Engineering health

- **UI behaviour has no automated tests.** 55 components, zero component tests, no `tests/e2e/` (verified). Most of this
  session's real bugs were found only in a browser (a dialog dropping fields on save, persona activation, selectors).
  The ad-hoc Playwright scripts used here should become `tests/e2e/` smoke tests in CI: seed → export → re-import;
  agent create appears in an open tab; conflict; branch; theme persists. **M.**
- **`StateSync` is the riskiest file and the least testable.** 327 lines inside a React effect; only its pure parts
  (diff, merge) have tests. The ordering rules that matter (pull before save, when `baseRev` may advance, re-baselining
  after a pull) were verified live, not in a test. Extract an engine with injected `fetch`/store/clock so those rules
  are unit-tested. **M.**
- **CI doesn't build.** It runs lint, typecheck, unit and API tests, but never `next build`, and has no `npm audit`
  gate; both would have surfaced item 1. Add both.
- **Docs drift.** The README says "60 unit tests" (now 389), its roadmap is stale, its structure listing omits
  `lib/cards`, `lib/sync`, `mcp/`. `docs/merge-characterbinder.md` is now history and should say so. `docs/memory-design-notes.md`
  is already labelled a snapshot.
- **Size.** `lib/db/store.ts` is 1,137 lines and `lib/chat/generation.ts` is 573. Splitting the store by drawer
  would match how the code is already organised.
- **Dependencies.** `npm audit --omit=dev` reports the Next items above; the rest are dev-tooling transitives that
  `npm audit fix` handles without breaking changes.

### Measured and fine (not findings)
- Orphan-memory purge on every save: **1.9 ms per call with 45,000 facts**, against 0.16 ms for the write itself.
  I suspected this would not scale; it does.
- Polling: six small-table scans per 3 s per visible tab (the `rev > ?` filter is unindexed, which is fine at this size); negligible.
- The guard's behaviour on odd paths (`//`, percent-encoding) is correct in production.
